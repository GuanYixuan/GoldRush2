# 双账号对称观察方案备忘

本文记录主号与观测账号配合进行机理建模数据采集的站位方案。目标是利用官方地图的横轴、竖轴对称性，在不依赖 90 度旋转对称的前提下，提高金币/炸弹生成观测效率。

## 基本判断

- 只信任横轴、竖轴对称，以及由二者推出的中心对称。
- 不采用 90 度旋转对称作为建模先验。
- 对称性用于绑定分布参数、合并统计样本，不用于补齐单局单轮真实状态。
- 主号与观测账号应各下载一份玩家视角 replay，离线合并双方视野后再做分析。

对称变换定义：

```text
H(r,c) = (16-r, c)
V(r,c) = (r, 16-c)
C(r,c) = (16-r, 16-c)
```

其中 `H` 为横轴对称，`V` 为竖轴对称，`C=H(V)=V(H)` 为中心对称。

## 已验证地图性质

使用主号只读拉取最近公测对局列表，并分别下载 `地图1`、`地图2` 各 20 局可解析 replay 的第二行静态地图进行检查。该操作未使用观测账号 key，未提交策略，未发起对局。

样本概况：

- 最近主号公测对局共 `328` 局。
- 可解析 replay 中，`地图1` 有 `197` 局，`地图2` 有 `131` 局。
- 本次每张地图抽取最近 `20` 局。
- 两张地图各自都只有一个静态地图变体。

检查结论：

- `地图1` 的静态障碍 `1` 满足横轴、竖轴、中心对称。
- `地图2` 的静态障碍 `1` 满足横轴、竖轴、中心对称。
- 两张地图的静态 `2` 不满足上述对称性。
- 两张地图的完整静态地图值不满足上述对称性。

因此，后续站位和可达性设计只应把静态障碍 `1` 作为障碍约束。静态 `2` 按 `gamerules/replay.md` 的结论处理，不视为障碍，也不作为地图对称性的证据。

## 主采集布局

首选四点布局：

```text
A = {(4,3), (4,11), (12,13), (13,4)}
```

在 `地图1` 和 `地图2` 上均已验证：

- 四个点都不是静态障碍 `1`，可作为站位目标。
- 四个 9x9 视野的直接并集覆盖 `281/289` 个格子。
- 直接漏掉的 8 个格子为：

```text
(0,16), (1,16), (2,16), (3,16),
(4,16), (5,16), (6,16), (7,16)
```

- 上述 8 个漏格的中心对称格全部在直接视野内。
- 因此该布局满足：

```text
U ∪ C(U) = 全图
```

由于横轴、竖轴对称也被采用，该布局也满足：

```text
U ∪ H(U) ∪ V(U) ∪ C(U) = 全图
```

这里的含义是覆盖了对称商空间的参数观测需求，而不是恢复每一轮的真实全图状态。

## 镜像布局

建议交替使用 `A` 与其中心镜像布局：

```text
C(A) = {(12,13), (12,5), (4,3), (3,12)}
```

该镜像布局在 `地图1` 和 `地图2` 上也已验证：

- 四个点均可站。
- 直接覆盖 `281/289` 个格子。
- 直接漏掉的 8 个格子为：

```text
(9,0), (10,0), (11,0), (12,0),
(13,0), (14,0), (15,0), (16,0)
```

- 漏格的中心对称格全部被观测。

交替采样的目的：

- 检验中心对称参数共享是否成立。
- 降低固定站位对局部生成、NPC 轨迹、炸弹触发的系统性偏差。
- 为 `region 2` vs `region 4`、`region 3` vs `region 5` 的统计比较提供成对样本。

## 双账号实现要求

单个玩家视角 replay 通常只包含本方两个角色的联合视野。四点布局需要主号和观测账号各贡献两个角色，因此必须：

- 双方都运行受控观察策略。
- 同一局分别下载主号视角 replay 与观测账号视角 replay。
- 离线按 `game_id`、`round`、玩家视角合并可见格。
- 保留每个格子的观测来源，不要只保存合并后的单值。

建议每轮至少记录：

- 主号可见 mask。
- 观测账号可见 mask。
- 合并可见 mask。
- 每个可见格的 `grid` 值。
- 玩家角色位置、NPC 位置、敌方可见位置。
- `snapshot.regions[].gold_generated` 等区域统计。
- 当前使用的布局编号：`A` 或 `C(A)`。

## 建模边界

可以使用的对称建模约束：

```text
lambda(r,c) = lambda(H(r,c))
lambda(r,c) = lambda(V(r,c))
lambda(r,c) = lambda(C(r,c))
```

但这些约束只应理解为分布参数共享。除非后续数据强力证明逐局状态严格对称，否则不能假设：

```text
G_t(r,c) = G_t(C(r,c))
```

第一阶段应优先检验：

- `region 2` 与 `region 4` 的 `gold_generated` 分布是否一致。
- `region 3` 与 `region 5` 的 `gold_generated` 分布是否一致。
- 镜像格的金币出现概率、金币数量分布是否一致。
- 镜像格的炸弹刷新概率是否一致。
- 站位格及其邻域是否存在驻留导致的系统偏差。
- NPC 占据率和转移概率是否破坏观测对称性。

## 数据落盘建议

- 原始下载 replay 放入 `mechanism/data/raw/`，保持平台返回原样。
- 合并视野、事件反推、特征表写入 `mechanism/data/processed/`。
- 原始数据和生成产物默认不进入 git。
- 如需记录采集批次，可另建 manifest，至少包含 `game_id`、地图、布局、双方模型名、下载来源账号、采集时间。

## 平台提交与采集流程

平台公测接口不是“上传版本后再单独发起对局”的形态。主号与观测账号采用如下流程：

1. 主号直连调用 `POST /api/user/add_model_4`，上传当前布局的公开 probe，供他人挑战。
2. 观测账号经 `OBSERVER_PROXY` 调用 `GET /api/user/get_model_list_4`，从可挑战列表中解析主号公开模型的 `model_id`。
3. 观测账号经 `OBSERVER_PROXY` 调用 `POST /api/user/add_model_1`，每局上传观测账号本局 probe，并传入 `model_id` 与 `map_id`，由接口立即创建对局。
4. 对局解析完成后，主号直连下载主号视角 replay，观测账号经 `OBSERVER_PROXY` 下载观测账号视角 replay。

环境变量位置：

- 仓库根目录 `.env`：主号 `LOGIN_KEY`。
- `mechanism/scripts/observer/.env`：`OBSERVER_KEY` 与 `OBSERVER_PROXY`。

脚本边界：

- `publish-main` 会修改主号公开代码，必须显式确认。
- `run` 会由观测账号上传本局代码并创建对局，必须显式确认。
- `doctor`、`resolve-main`、`fetch` 为只读或本地落盘操作，不提交策略、不发起对局。
