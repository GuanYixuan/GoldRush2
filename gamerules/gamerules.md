## 规则正文

### 赛事流程

- 线上报名：即日起至 8.14。
- 模拟赛：8.15 至 8.16。
- 公测阶段：7.20 至 8.21。
- 线上初赛：8.17 至 8.21。
- 决赛：9.6，北京 office；FAQ 说明决赛支持远程。

公测阶段：

- 官网地址：`http://47.103.127.219/`。
- 选手可登录官网上传代码调测。
- 代码可随时更新版本。
- 选手可主动挑战其他选手上传的策略，赛后生成比赛日志，并可通过官网回放。
- 官方提供若干公测对局日志，路径为 `/share/data.tar.gz`。
- 官方不会下发模拟器，随机分布不会公开。

初赛：

- 引擎自动汇总代码并进行对战。
- 所有参赛队伍进行循环赛。
- 每支队伍与其他所有队伍进行 1v1 金币争夺赛，按胜率排名。
- FAQ 中提到：初赛循环赛地图数量、每对选手局数等暂不透露；官方会考虑交换出生边、使用相同随机种子进行镜像对局。

决赛：

- 初赛排行榜前 16 支队伍晋级。
- 淘汰赛赛制，两两对决，胜者晋级，最终决出冠亚季军。

### 基础地图

- 战场为 `17x17` 网格地图。
- 两名玩家各控制两个角色。
- 角色出生点位于主对角线或副对角线的两端。
- FAQ 补充：P1 位于主对角线，P2 位于副对角线。
- 地图上存在障碍物、炸弹及 NPC。
- 障碍物所在网格不可到达。
- 障碍情况可通过自行发起对局分析；官方未公开障碍物生成方式。

### 区域划分

公测和初赛固定使用官方 FAQ 图中的 5 区域划分方法。按 `row`、`col` 均为 `0..16` 坐标整理如下：

| 区域 | 名称 | 尺寸 | 坐标范围 |
| --- | --- | --- | --- |
| 1 | 中央 | `9x9` | `row=4..12, col=4..12` |
| 2 | 上 | `13x4` | `row=0..3, col=0..12` |
| 3 | 左 | `4x13` | `row=4..16, col=0..3` |
| 4 | 下 | `13x4` | `row=13..16, col=4..16` |
| 5 | 右 | `4x13` | `row=0..12, col=13..16` |

### 网格状态

`GameInput.grid` 为 `17x17` 数组，含义如下：

| 值 | 含义 |
| --- | --- |
| `-5` | 迷雾，视野外 |
| `-3` | 炸弹 |
| `-1` | 障碍物 |
| `0` | 空地 |
| `>=1` | 金币，值为该格金币数量 |

补充规则：

- NPC 不在 `grid` 中标记，通过 `visible_npcs` 列表提供。
- 金币在 `grid` 上应有完整表达；实体位置通过其他数组或字段表达。

### 视野

- 全局信息不对玩家公开。
- 每个角色默认视野为以自身为中心的 `5x5` 区域。
- 每轮传入的 `GameInput.grid` 只包含两个己方角色在本轮决策时最终位置的当前视野。
- 接口不会提供上一轮移动过程中沿途看到的视野增量，也不会提供已探索地图。
- 玩家可花费金币扩展视野范围。
- `vp=0`：不购买视野。
- `vp=1`：同时为两个角色购买 `7x7` 视野，当前价格为 2 金币。
- `vp=2`：同时为两个角色购买 `9x9` 视野，当前价格为 3 金币。
- 视野购买下回合生效。
- 购买视野的生效时长为 1 回合。
- 可以连续购买视野。
- 视野费用在对局结束后结算。
- [数据推断] **视野购买不要求当前毛金币足额**：官方示例日志中存在玩家当前毛金币为 `0` 时购买 `7x7` 视野仍被计费并在下一回合生效的样本；平台对局 `35104` 中也存在对手当前毛金币小于 `3` 时仍按 `vp=2` 计入 `3` 点 `vision_spent` 的样本。

### 回合流程

每个回合的完整顺序：

1. 生成新的金币或炸弹。
2. 调用玩家策略。
3. 策略耗时短的玩家行动。
4. NPC 行动。
5. 策略耗时长的玩家行动。

补充规则：

- 每回合两名玩家拿到的是行动前的同一份地图状态。
- 每回合按决策耗时从小到大依次执行移动。
- 同一网格的金币或炸弹由先执行者获取或触发。
- NPC 行动顺序位于两名玩家之间。
- 如果双方决策耗时在纳秒级完全相同，则 P1 先手。

### 移动规则

- 每名玩家的两个角色初始金币均为 0。
- 每轮两个角色共分配 `S=6` 次移动机会，可任意分配。
- 动作编码：

| 值 | 动作 |
| --- | --- |
| `0` | 上 |
| `1` | 下 |
| `2` | 左 |
| `3` | 右 |
| `4` | 不动 |

- `k` 为分割点：角色 0 执行 `actions[0:k]`，角色 1 执行 `actions[k:S]`。
- `order=0` 表示角色 0 先执行，`order=1` 表示角色 1 先执行。
- `order` 的精确语义是：一个角色执行完全部动作后，另一个角色再执行。
- 非法移动不执行，后续移动照常进行。
- 非法移动包括越界、碰障碍物、碰其他玩家角色。
- FAQ 补充：两个玩家一共 4 个角色之间两两不能重叠。
- 可以进入本回合中其他角色已经腾出的格子。
- 一个角色走完后，只占用最终停留格；路径经过的其他格子不会继续占用。
- 发生碰撞时，该角色当前这一步不执行，后续步仍会继续尝试执行。
- 同一个玩家的两个角色不能互相穿过、交换位置。
- 碰撞按 `order` 逐步实时判断，不是整条路径统一判定。
- 不同角色在同一回合路径有交集不一定会碰撞；只有进入另一个角色当前停留的格子才会碰撞。
- NPC 与玩家角色之间可重叠，NPC 不阻挡玩家移动。

### 金币生成与拾取

- 中心 `9x9` 区域每回合随机生成一定数量金币。
- 每若干轮在 `9x9` 区域外随机生成一定数量金币。
- 金币生成分布不公开。
- 角色或 NPC 从其他网格移动到有金币的网格，获得该格 `C=65%` 的金币，向上取整。
- 只要从一个格子移动到另一个有金币的格子，就可以吃到新移动到格子上的金币。
- 同一角色离开再进入可以重复拾取。
- 金币直接生成在角色脚下时，不会自动拾取。
- 同一个位置不会同时有炸弹和金币。
- 同时有金币和踩踏时，先吃金币，再发生踩踏扣除金币。

### 炸弹

- 角色移动到炸弹网格时，损失当前持有金币的 `X=10%`，向上取整。
- 炸弹触发后消失。
- 触发炸弹后，角色可继续行动。
- 每 `Y=20` 轮刷新一次炸弹。
- 炸弹不会刷新在玩家、NPC、金币或已有炸弹所在格。
- 炸弹生成在角色脚下时，原地停留不会触发。
- 同一个位置不会同时有炸弹和金币。
- 同一个位置不会同时有炸弹和大于等于 3 个 NPC。
- FAQ 中“整套炸弹重采样是否沿用正式赛”等问题，官方答复为无法透露。

### NPC

- 开局时所有 NPC 出生在地图最中央。
- NPC 总数 `A` 在公测期间为 7。
- 每个 NPC 每轮最多移动 `B=3` 步。
- NPC 与玩家角色一样行动，参与金币争夺。
- NPC 之间、NPC 与玩家角色之间可重叠。
- NPC 参与金币争夺，但不计入选手胜负判定。
- NPC 持有的金币不参与玩家之间的胜负结算。
- [数据推断] **NPC 会触发炸弹**：NPC 移动进入炸弹格会使炸弹消失；NPC 是否因此扣除自身持币暂不能确认。
- NPC 的移动策略不公开。
- NPC 内部顺序等更多信息不公开。
- `visible_npcs` 中 NPC 的 `id` 跨回合不变；不可见时位置为 `(-1,-1)` 或不出现在可见列表中，具体以接口为准。

### 拥挤踩踏

- 玩家角色进入有超过 2 个 NPC 的格子时，因拥挤踩踏损失当前 `N=5%` 金币，向上取整。
- FAQ 补充：只有玩家行动后走到一个 NPC 个数 `>=3` 的格子才会触发。
- NPC 在玩家进入之后聚集，不会追溯处罚。
- 同时有金币和踩踏时，先吃金币，再发生踩踏扣除金币。

### 快照

- 每 `D=5` 轮发布全局各区域的快照信息。
- 每 `D` 轮额外提供全局区域快照。
- 快照信息包括 NPC。
- 快照反映的是上几轮的情况。
- `snapshot_valid=1` 表示本轮有新快照，`snapshot_valid=0` 表示无新快照。
- C++ 中本轮无快照时，`Snapshot.window_begin=-1`。
- Python 中无快照时，`snapshot` 为 `None`。

`RegionStat` 字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 区域编号 `1..5` |
| `enter` | 窗口内进入该区域的角色次数 |
| `leave` | 窗口内离开该区域的角色次数 |
| `gold_generated` | 窗口内该区域生成的金币总量 |
| `gold_collected` | 窗口内该区域被拾取的金币总量 |
| `gold_remaining` | 该区域地面当前剩余金币 |
| `occupants` | 该区域当前角色数 |

进入次数定义：

- 任意一个玩家的角色或 NPC，在本回合开始前不在某区域，本回合结束后在该区域，则该区域累计一次进入次数。

离开次数定义：

- 任意一个玩家的角色或 NPC，在本回合开始前在某区域，本回合结束后不在该区域，则该区域累计一次离开次数。

### 获胜规则

- 每场比赛固定 500 轮。
- 结束时金币总量最多的玩家获胜。
- FAQ 补充：每局胜负按毛金币减去视野花费后的剩余金币计算。
- `gold_opp` 是对手两角色毛金币总和。
- 玩家策略在游戏过程中无法得知对方视野花费。
- 游戏结束后，回放可以查看视野花费。
- 金币总数相等时，P90 延迟更低的玩家获胜。

### 时间限制与状态保存

- 每轮标准限时 300ms。
- 另有 `T=60` 秒总思考时间池。
- 只有每回合超出 300ms 的部分会计入时间池；不超过 300ms 不计入时间池。
- 时间池耗尽则判负。
- P90 仅统计 `moveDecision`。
- 如果第一次 `moveDecision` 中做初始化，初始化时间会计入。
- 如果在 `moveDecision` 中做日志 I/O，日志 I/O 时间会计入。
- 加载选手策略的时间上限为 10 秒。
- 策略对象或共享库会被直接加载进内存，不会每轮执行后释放。
- 策略对象或共享库会保持到全部比赛打完，或程序异常退出后释放。
- 选手可在每次代码被调用时自行管理资源。
- Python 可实现 `__init__`。
- C++ 可使用全局变量初始化。

### 异常与判负

- 每轮必须正确返回决策。
- 格式非法、运行异常、超时会直接判负。
- 无单轮容错。

### 编程接口

#### C++ 提交与 ABI

- C++ 提交选手策略 `.so` 文件运行。
- `game_api.h` 是正式 C++ ABI。
- C++ `.so` 文件大小限制为 16MB。
- 编译机和运行机相比，运行机除 CPU 未开超线程外没有其他区别。

入口函数：

```cpp
extern "C" GameOutput moveDecision(const GameInput* input) {
    GameOutput output = {};
    // 实现决策逻辑
    return output;
}
```

核心结构：

```cpp
struct Position { int row; int col; };

struct NpcInfo {
    int id;       // NPC 编号，跨回合不变；空槽为 0
    Position pos; // NPC 位置；不可见时 (-1,-1)
};

struct RegionStat {
    int id;             // 区域编号 1-5
    int enter;          // 窗口内进入该区域的角色次数
    int leave;          // 窗口内离开该区域的角色次数
    int gold_generated; // 窗口内该区域生成的金币总量
    int gold_collected; // 窗口内该区域被拾取的金币总量
    int gold_remaining; // 该区域地面当前剩余金币
    int occupants;      // 该区域当前角色数
};

struct Snapshot {
    int window_begin;      // 统计窗口起始轮；本轮无快照时为 -1
    int window_end;        // 统计窗口结束轮
    RegionStat regions[5];
};

struct GameInput {
    int round;                    // 当前回合，从 0 开始
    int grid[17][17];             // 网格信息
    Position my_units[2];         // 我方角色 0、角色 1 的位置
    int my_units_gold[2];         // 我方角色 0、角色 1 各自持有金币
    int gold_opp;                 // 对手两角色金币总和，毛金币
    Position visible_enemies[2];  // 视野内敌方角色位置，不可见时 (-1,-1)
    int num_visible_npcs;         // visible_npcs 中有效条数
    NpcInfo visible_npcs[A];      // 可见 NPC 列表
    int snapshot_valid;           // 1=本轮有新快照；0=无
    Snapshot snapshot;            // 全局区域快照
};

struct GameOutput {
    int actions[S]; // S 步动作
    int k;          // 角色 0 走 actions[0:k]，角色 1 走 actions[k:S]
    int order;      // 0=角色 0 先执行，1=角色 1 先执行
    int vp;         // 0=不买，1=买 7x7，2=买 9x9
};
```

#### Python 接口

- Python 提供 `.py` 文件。
- FAQ 明确：Python 参照 `player.py`，返回长度为 9 的 `list`。
- 长度 9 的返回值可按 `actions[0..5] + [k, order, vp]` 理解。

### NPC 会触发炸弹

- 结论：当前官方 full 日志支持“NPC 移动进入炸弹格会触发炸弹，并使炸弹消失”。但 NPC 是否因炸弹扣除自身持币，现有日志缺少可验证的 NPC 累计持币字段，不能确认。
- 数据来源：`official_sdk/data/full/g0.txt`、`g1.txt`、`g2.txt`。
- 样本范围：`1500` 个回合，`10500` 条 NPC 跨回合移动记录。
- 推断方法：用 `start.npcs[].position`、`end.npcs[].actions` 和障碍/边界规则重放 NPC 移动，`10500/10500` 条均能匹配 `end.npcs[].position`；再按 `end.dispatch_order` 同步重放玩家和 NPC 的行动，统计每个炸弹格的首个进入者。full 样本中共有 `397` 个 start 炸弹在 end 消失，全部可由行动重放解释，其中 `288` 次首个触发者为玩家，`109` 次首个触发者为 NPC。
- 置信度：高。该结论基于官方提供的上帝视角日志，且没有观察到 NPC 进入炸弹格后炸弹仍保留的反例。
- 已知反例或风险：官方 FAQ 对“NPC 是否会触发炸弹”答复为无法透露，因此正式赛是否保持同一实现仍不能由官方文本保证；同时 `burned` 只统计玩家角色金币损耗，不能用于判断 NPC 触发炸弹时是否扣除 NPC 持币。

### 视野购买不要求当前毛金币足额

- 结论：当前官方示例日志和平台对局日志支持“视野购买费用不从当前毛金币即时扣除，且不要求当前毛金币足额后才允许购买”。视野费用会累计到 `vision_spent`，并参与赛后净金币结算；净金币可以为负数。
- 数据来源：`official_sdk/data/user/g*.txt`；平台回放 `game_id=35104`。
- 样本范围：`official_sdk/data/user/g*.txt` 的 `197` 个玩家视角日志中，共观察到 `36438` 次 `vision_spent` 增量事件，其中 `1476` 次发生时该玩家当回合开始毛金币小于本回合新增视野费用。`game_id=35104` 共 `500` 回合，对手 `abc13` 的 `vision_spent` 每回合增加 `3`，最终 `gold=59`、`vision_spent=1500`、净金币为 `-1441`。
- 推断方法：逐回合比较同一玩家 `start.players[].vision_spent` 与 `end.players[].vision_spent` 的差值，并与该玩家当回合 `start.players[].gold` 比较；再用下一回合 `start.vision_r` 检查视野半径是否扩大。例如 `official_sdk/data/user/g4.txt` 第 `5` 回合，`player1` 当回合开始 `gold=0`、`vision_spent=0`，回合结束 `gold=0`、`vision_spent=2`；第 `6` 回合 `start.vision_r={"1":3}`，说明这次 `7x7` 视野购买在 `0` 金币时仍被计费并于下一回合生效。`game_id=35104` 中，第 `0..9` 回合对手当回合开始 `gold=0` 且每回合 `vision_spent += 3`，第 `10..13` 回合开始 `gold=2` 且仍每回合 `vision_spent += 3`，说明 `vp=2` 也不会因当前毛金币小于 `3` 而不计费。
- 置信度：高。该结论直接反驳“当前金币不足则不能购买视野”的通用限制，并与官方“视野费用在对局结束后结算”的规则一致。
- 已知反例或风险：`game_id=35104` 中当前登录账号为 `viewer_side=2`，完整视角在我方 `player142`，因此不能用该局直接观察对手 `abc13` 的下一回合 `vision_r` 是否扩大；但 `vision_spent += 3` 和最终负净金币足以确认平台接受并累计 `vp=2` 费用。
